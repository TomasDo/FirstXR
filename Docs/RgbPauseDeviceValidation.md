# RGB Pause Device Validation (2026-09-29)

This run used a Beam Pro X4100 + XREAL One Pro. The APK used for the continuous five-minute observation had SHA-256 `e75b5db8370a3d967c86bf9a93c44630a5ef7f086400ca2b53c6c505340a9a85` (installed at 18:08:08). An encoder crash was subsequently found when XR-only streaming had no left-eye frame. After adding a startup guard, the current `Builds/First XR.apk` had SHA-256 `4670cdf7740a2c05657eaa91cabbddb5309c128d96cb67b902e956e56bd6a5d8` (replacement installed at 18:26:11). Final Unity EditMode tests passed 121/121; navigation simulator tests passed 51/51.

`RgbFeaturePolicy.Enabled` disables all RGB features. The camera service returns before permission requests, camera object creation, capture, or retries; preview, gesture slicing, MediaPipe/GPU readback, and RGB RTP are blocked. Local buttons display "RGB paused" and are disabled. An RGB enable command sent to the device returns `ACK accepted=false` and `ObservationStatus.error=RGB paused`; the simulator's media receiver was disabled after testing. The XR-only mirror code path remains, but device evidence of a valid left-eye image had not yet been obtained.

After connecting to the same navigation simulator and loading the model and CT assets, sampling continued for 310 seconds (ten complete 30-second windows). The application and the glasses' external display remained connected. Log counts for native RGB reads, MediaPipe, GPU readback, and fatal exceptions were all zero. Across 16,346 UI frame samples, window p95 values were 20.8–26.8 ms, the longest frame was 94.4 ms, and no frame exceeded 100 ms. Switching between the Beam Pro Monitor and Connection pages worked. After the simulator changed the CT slice offset from 39.6 mm to 40.6 mm, Beam Pro correctly displayed 40.6 mm; the offset was then restored to 39.6 mm.

Navigation latency warnings still occurred. Across the ten windows, "Navigation data delayed" was entered 18 times and "Navigation data interrupted" 15 times; maximum navigation frame age was 3615.6 ms. The maximum gRPC receive interval was 3704.6 ms, and maximum source frame age at reception was 3568 ms. Window p95 latency from receipt to application in Unity was 17.4–21.7 ms. The phone clock was approximately 92 ms behind the host (best ADB round trip: 58.8 ms), which cannot explain a backlog measured in seconds. During the same period, 170 local samples taken once per second on the simulator showed a maximum generated frame age of 40.4 ms and sequence growth of 26–29 per second. The data points to a transport/receive backlog after simulator generation and before Unity receipt; gRPC internal queues, networking, and phone-side HTTP/2 reads have not yet been distinguished.

The navigation simulator console previously stopped the old stream before handling a new RGB or combined video request. As a result, even if the client rejected RGB, the preceding stop command had already terminated an existing XR mirror. The actual simulator source now rejects unsupported requests in advance based on the client's capability declaration. All 51 tests passed, including new coverage confirming that RGB-only and combined requests leave an existing XR-only stream unchanged. **The running Node service had not yet been restarted and was still executing the old code; this fix takes effect only after restart.**

After the five-minute observation, a separate XR-only mirror request received a successful ACK, immediately followed by SIGABRT in the Beam Pro process from an uncaught exception on the XREAL SDK encoder's rendering thread. The left-eye frame was unavailable at that time, and the server received no valid RTP. The final APK adds a guard that refuses to start the encoder without a valid left-eye frame. Device retesting returned a failed ACK with a clear reason, and the application continued running. This guard does not establish that encoding valid XR left-eye frames has been verified; that remains open.

The external display in this run was a secure display, so ADB could not capture the glasses' image. Text in the glasses and XR mirror content still require direct visual inspection. There is no RGB-enabled baseline collected with the same sampling method, so these frame timings cannot be interpreted as a quantified before/after improvement. The navigation latency thresholds of 200/500 ms were not changed.
